🚰 Leakage in cross-validation — the bug that makes your model look better, which is why it survives. Scale the features, or select them, or impute, before splitting, and every fold's "held-out" data has already touched the training statistics. The score goes up, nothing errors, and the gap only appears in production. This page measures it rather than warning about it: the same data and the same model, evaluated correctly and four wrong ways, against a true out-of-sample score computed from a held-back set the pipeline never sees. The worst case is not scaling — it is feature selection on the full dataset, which on pure noise with no signal at all reports a cross-validated accuracy far above chance. That is the diagnostic worth keeping: run your pipeline on random labels, and if it scores above chance, the leak is in the pipeline and not in the data. Grouped and time-ordered data get their own splitters, because a random KFold on either is leakage by construction. Pure vanilla JavaScript, one file, offline.

Signal strength 0 means the labels are random — there is nothing to learn, and every honest number below should sit at 50%.

The bug that makes your model look better

Every other bug in a modelling pipeline announces itself by making the number worse. Leakage makes it better, which is why it ships: nobody investigates a pleasant surprise, and the code that causes it looks like tidy engineering.

scaler = StandardScaler().fit(X)          # <- on ALL the data
X = scaler.transform(X)
scores = cross_val_score(model, X, y, cv=5)

Every fold's "held-out" rows contributed to the mean and standard deviation used to transform the training rows. The test set is no longer held out; it has been consulted.

The severity ladder

Not all leaks are equal, and the ordering surprises people:

  • Scaling before the split — usually mild. Two moments estimated from a few extra rows barely move.
  • Imputing before the split — worse, because a missing value is filled from a statistic that saw the answer.
  • Target encoding before the split — much worse. You are putting a function of the label directly into a feature.
  • Feature selection before the split — catastrophic, and it is the one this page is built around.

Why selection is the catastrophic one

With p features and n samples, some features correlate with the labels by chance. Choose the best ones using all the data and you have chosen features that happen to fit the rows you are about to evaluate on. On pure noise — labels shuffled, nothing to learn — this reports a cross-validated accuracy well above 50%. The model has learned nothing, and the score is real in the sense that the arithmetic is correct.

The effect grows with p. More candidates means a better chance that some of them fit the noise, so the more thorough your feature engineering, the worse this gets — which is exactly backwards from what the effort was supposed to buy.

The cheapest test you can run

y_shuffled = shuffle(y)
score = your_whole_pipeline(X, y_shuffled)
assert score ≈ chance

Shuffle the labels and re-run everything. There is now provably no signal, so an honest pipeline must score at chance. Anything above it is leakage, and you have found it without a held-out set, without a production comparison, and without knowing which step is guilty.

It is three lines. It should be in every notebook that reports a cross-validated number.

When the splitter is the leak

Moving preprocessing inside the fold does not help if the split itself is wrong:

  • Grouped data. Several rows per patient, user or document. A random split puts the same entity on both sides, and the model recognises the entity rather than the pattern. Use GroupKFold.
  • Time series. A random split trains on the future to predict the past. Use a forward-chaining split, and honour any gap between the feature window and the label.
  • Duplicates. Near-identical rows are grouped data you have not noticed.

The page measures both, because the inflation from a wrong splitter is often larger than the inflation from wrong preprocessing — and it is the one that a Pipeline object will not save you from.

What actually fixes it

Put every fitted transformation inside the fold. In scikit-learn that is what Pipeline is for — not tidiness, correctness:

pipe = Pipeline([("scale", StandardScaler()),
                 ("select", SelectKBest(k=20)),
                 ("model", LogisticRegression())])
scores = cross_val_score(pipe, X, y, cv=GroupKFold(5), groups=groups)

Everything that learns from data — a mean, a threshold, a vocabulary, a set of selected columns — must learn inside the fold. If it has a .fit(), it belongs in the pipeline.

The honest caveat about this page

The classifier here is a small ridge-regularised linear model written from scratch, and the effect sizes depend on it. What does not depend on it is the structure: a pipeline with no signal to learn cannot honestly beat chance, and every number on the page is checked against a held-back set the pipeline never touches.

🔨 How it is built

1. A ground truth the pipeline cannot see

const { train, holdout } = splitOnce(data, 0.5);   // holdout is set aside FIRST
const cvScore   = crossValidate(train, pipeline);  // what the pipeline reports
const trueScore = fitAndScore(train, holdout);     // what it is actually worth

Without that second number the page would be comparing pipelines to each other, which cannot tell you which one is right. The holdout is split off before anything else happens and is never passed to any fitting step.

2. The four wrong pipelines, as real code paths

scaleBeforeSplit:  scaler fitted on ALL rows, then k-fold
selectBeforeSplit: top-k features chosen using ALL labels, then k-fold
imputeBeforeSplit: column means over ALL rows, then k-fold
targetEncodeFirst: a per-group mean of y computed over ALL rows

Each is the same three lines in a different order, which is the point — none of them looks like a mistake in review.

3. Selection, and why it is the worst

function selectTopK(X, y, k){
  const scored = columns(X).map((col, j) => ({ j, r: Math.abs(correlation(col, y)) }));
  scored.sort((a, b) => b.r - a.r);
  return scored.slice(0, k).map(s => s.j);
}

Run that on the full dataset and the chosen columns are the ones that fit the rows you are about to score on. The test asserts that with zero signal this pipeline still beats chance — if it ever stopped doing so, the harness would be broken, because that inflation is arithmetic rather than luck.

4. The null-label diagnostic, as an assertion

const shuffled = shuffleLabels(data, rnd);
assert(Math.abs(correct(shuffled) - 0.5) < 0.06);     // honest pipeline: chance
assert(selectFirst(shuffled) > 0.6);                   // leaky pipeline: not chance

Two assertions in opposite directions. The first says the harness is sound; the second says the bug is real. Either alone proves much less than the pair.

5. Splitters that are wrong by construction

// grouped: every row of a group must land in the SAME fold
function groupKFold(groups, k){ ... }

// time: fold i trains on [0, cut) and tests on [cut, next)
function forwardChaining(n, k){ ... }

Both are checked structurally rather than by score: no group id appears in two folds, and no test index is ever smaller than a training index. A splitter that produces a good number while violating either of those is producing a good number for the wrong reason.

6. What the tests pin

assert(cv(correct) ≈ trueOutOfSample(correct));    // the honest one is honest
assert(cv(selectFirst) > cv(correct) + 0.15);      // and the leak is large
assert(cv(selectFirst) > trueOutOfSample(selectFirst) + 0.2);
assert(inflation grows with p);                    // more features, worse leak
assert(no group spans two folds);
assert(no time fold trains on the future);
